# 取证模型：证据要浅、确定、有界

> 回答三个问题：证据怎么取、取到什么程度、会不会无限递归核验。
> 结论先行：**证据只取"边界事实"，不证明智能体的思考；核验深度固定为 1，永不校验校验器。**
> 你担心的"逆向/递归"是真实风险，但它的解法不是"更聪明地验"，而是**把可判定的部分写死，把不可判定的部分交给一次单发语义判定**。

---

## 1. 先说结论（一句话版）

| 要验的 | 怎么验 | 深度 |
| :-- | :-- | :-- |
| 结构（做到哪一步） | Todo 清单状态 | 0（自述，只做展示与分流） |
| 边界事实（有没有发生） | 确定性检查：exit code / 文件哈希 / HTTP / 注册表 / git | 1（观察一次，不追证据的证据） |
| 语义（是否"合适"） | 一次单发模型判定，输入是**冻结快照**，输出结构化结论 | 1（判完即止，不复议） |
| 重大不可逆 | 人 | 1（人说了算） |

**不存在第 2 层**：不"核验校验器"，不"核验证据的来源"，不"让另一个模型检查第一个模型的判定"。这就是全部。

---

## 2. 为什么不能无限递归（理论原因）

三个已成型的研究结论正好解释为什么"验证到底"不成立：

1. **Oracle 问题**：测试/验证需要一个"正确答案的来源"（test oracle）。没有 oracle，就无法判定行为对错；而 oracle 本身通常无法被形式化验证，否则会无限后退（[Test oracle](https://en.wikipedia.org/wiki/Test_oracle)）。
2. **可判定性边界**：对任意程序（更别说任意智能体）验证任意性质是不可判定的；工业界只能验证**有界性质**（超时、不变式、trace 上的谓词）。Runtime verification 的做法就是把性质写成可在 trace 上判定的谓词，然后由**有界监控器**判定（[Runtime verification](https://en.wikipedia.org/wiki/Runtime_verification)）。
3. **证明携带（PCC）的思路**：让生产者随产物提交一份**小证明**，验证方只需跑一个**小而快的检查器**，而不是重新推导一遍（[Proof-carrying code](https://en.wikipedia.org/wiki/Proof-carrying_code)）。SLSA 也是同一路：定义"受信任的构建平台"（trusted base），然后只验证产物与出处证明，而不是验证平台内部每一步（[SLSA provenance](https://slsa.dev/spec/v1.0/provenance)）。

对应到我们：

- **信任基**（trusted base）= 文件系统、git、命令退出码、HTTP 状态、数据库行数。这些是"直接可观察"的，不再追问"谁保证它们是真实的"——否则会退到操作系统/硬件，永远没有底。
- **证据 = 小证明**：一段 diff 摘要 + exit code + 哈希，而不是"把整个会话再读一遍让另一个模型复核"。
- **判定 = 小检查器**：确定性代码或一次模型调用。

## 3. 证据分级：E0–E4

| 级别 | 证据形态 | 获取成本 | 强度 | 用在哪 |
| :-- | :-- | :-- | :-- | :-- |
| **E0** | 自述（"我做完了"） | 0 | 极弱 | 只做展示，不参与判定 |
| **E1** | 产物存在 + 哈希 / 路径 | 极低（stat + sha256） | 中（证明"存在"，不证明"对"） | read、归档、通知 |
| **E2** | 确定性检查结果：exit code、测试报告、HTTP 200、行数、注册表 tag | 低（一次命令/一次 HTTP） | 高（证明"某个可判定事实成立"） | write-code、部署 |
| **E3** | 独立观察：git log、CI 记录、文件 mtime、外部系统状态 | 低–中 | 高（不依赖执行者自述） | 对账、补证 |
| **E4** | 人确认（点击/审批/抽样复核） | 高 | 最高（语义与责任） | destructive、spend、标准有歧义 |

规则：**证据级别按 effect 和标准类型选，不是越高越好**。

| effect | 最低证据 | 说明 |
| :-- | :-- | :-- |
| read | E1 | 文件/接口存在即可 |
| write-code | E2 | 必须有可判定的检查（测试/构建/路径规则） |
| external | E2 或 E3 | healthz、镜像 tag、发布记录 |
| spend | E4 | 人确认 |
| destructive | E4 | 人确认 + 备份存在（E2 辅助） |

## 4. 取证流程（谁、何时、存哪、怎么判）

```text
派发时：ApprovedPlan 里每条 acceptance 已声明「怎么取证据」(checker)
执行完：执行者/适配器跑 checker → EvidenceRecord
     ↓
验证器：读 EvidenceRecord，按 criterion 判 pass/fail/unknown
     ↓
写入执行账：criteriaResults[] + evidenceRef + evidenceHash
```

**EvidenceRecord 只允许这几种形态**（可枚举，不能自由发挥）：

```ts
type EvidenceKind =
  | { kind: 'exit'; cmd: string; code: number; stdoutRef: string }
  | { kind: 'file'; path: string; sha256: string; bytes: number }
  | { kind: 'http'; url: string; status: number; bodyRef?: string }
  | { kind: 'git'; commit: string; files: string[]; diffStat: string }
  | { kind: 'db'; query: string; rowCount: number }
  | { kind: 'text'; excerpt: string; sourceRef: string }   // 仅 E0/E3 兜底
```

限制：

- 每条证据带 `sourceRef`（日志文件/URL/命令），可点开看原文；
- `text` 是兜底，不得用于 confirmed 的唯一依据；
- 所有证据落盘并记哈希，卡关掉也不丢。

## 5. 有界性预算（防"取证失控"）

| 预算 | 值 | 为什么 |
| :-- | :-- | :-- |
| 每张卡证据条数 | ≤ 5 | 等于 acceptance 条数上限，多了说明标准写太碎 |
| 每张卡语义判定 | 0–1 次 | 只有 `evidence` 类标准才需要；判一次不复议 |
| 单条 checker 超时 | 10s | 超时记 `unknown`，不重试取证 |
| 总验证时长 | ≤ 30s | 超过就异步，面板显示"验收中" |
| 核验深度 | **固定 1** | 不验证证据来源、不验证校验器 |
| 递归 | **禁止** | 验证器不调用验证器；对账不以"对账结果"为证据 |

**不做什么**（写死，防跑偏）：

- 不为了"确认 exit code 是真的"去读 shell 历史；
- 不让模型去"检查日志里有没有造假"；
- 不为一条证据再开一个会话；
- 不用 LLM 判 exit code 这类机器项（浪费且不稳定）。

## 6. 那"直接相信会话模型 + todo"呢？

这其实是一个**真实的可选项**，而且不蠢：它把语义判断交给最懂上下文的模型，成本最低。关键是看清它的代价。

### 6.1 三种方案对比

| 维度 | A. 纯信任会话（todo 全绿=通过） | B. 边界取证（本文方案） | C. 混合（推荐） |
| :-- | :-- | :-- | :-- |
| 成本 | 最低（0 额外调用） | 低（几条命令/HTTP） | 低–中 |
| 延迟 | 0 | 秒级 | 秒级 |
| 语义能力 | 强（模型懂上下文） | 弱（只能判可判定项） | 强（语义项用一次模型） |
| 抗"标绿造假" | **弱**（自证） | 强（exit/文件说了算） | 强（结构自述 + 边界硬证） |
| 可审计 | 弱（只有自述） | 强（证据 + 哈希） | 强 |
| 可回归 | 弱（换模型结论会变） | 强（确定性） | 强（机器项不变） |
| 误判风险 | 中（模型可能被上下文带偏/注入） | 低（只判事实） | 低 |
| 实现复杂度 | 最低 | 中 | 中 |
| 责任归属 | 模糊（谁判的？） | 清晰（系统/秘书/人） | 清晰 |
| 失败可解释 | 中（"模型说完不成"） | 强（哪条 criterion 为什么） | 强 |

### 6.2 纯信任方案的真实问题

1. **自证**：执行者既做又判。A-core 的核心设计就是分离这三种角色，纯信任把这层设计拆了。
2. **Reward hacking**：只要完成率影响面板/KPI，模型就有动力把清单标绿。这不是模型坏，是指标设计的必然（Goodhart）。
3. **不可审计**：用户质疑"这算完成了吗"，你只能再问一次模型；第二次的答案可能不同，且没有证据可看。
4. **回归不可控**：换模型/换提示词，同一张卡的结论可能翻转，而且无法定位为什么。
5. **注入风险**：会话内容里有用户粘贴的外部文本，模型可能被其中的指令带偏；纯信任等于把这个风险直接放进验收。

### 6.3 但边界取证也有代价

- **标准必须写成可判定的**：这会把"diff 是否只涉及相关文件"从"让模型看"变成"路径前缀规则"。这其实是好事（shift-left），但需要一次性设计成本。
- **有些标准天生不可判定**："语气是否合适""方案是否更优"——这类只能 E4（人）或一次语义判定，不能硬套机器项。
- **证据本身也有成本**：跑测试、查注册表、算哈希都要时间。所以才有预算和抽样。

### 6.4 我推荐的折中（C）

**结构交给 todo，事实交给边界检查，语义交给一次单发判定，重大交给人。**

具体到我们的卡：

| 卡 | 验收标准 | 证据 | 级别 |
| :-- | :-- | :-- | :-- |
| c-42 提交代码 | `pnpm test` 退出码 0 | exit code + test.log 尾部 | E2 |
| | 不含密钥 | 对 diff 做正则（确定性） | E2 |
| | 仅涉及 scheduler 文件 | git diff 的路径前缀匹配 | E2 |
| c-43 删表 | 用户确认 | 审批记录（authority=user） | E4 |
| | 备份存在且行数匹配 | stat + db rowCount | E2 |
| c-45 部署 | healthz 200 | HTTP 状态 | E2 |
| | 镜像 tag == commit sha | 注册表 API | E2 |
| c-44 通知 | 无 | 不需要证据 | — |

注意：**这张表里几乎没有"语义判定"**。不是因为不需要，而是因为把标准写成可判定规则之后，语义项只剩极少数（比如"发布说明是否准确描述了变更"）。**能写成确定性规则的，绝不交给模型**——这是省钱的根源，也是你说的"系统性"。

### 6.5 什么时候可以"直接相信模型"

如果满足以下全部条件，可以只用 E0/E3，不做 E2：

1. effect = read 或纯通知；
2. 出错可逆、代价低；
3. 该卡不进入 KPI / 不作为判例；
4. 有抽样审计兜底（比如 10% 人工复核）。

这就是"分级信任"：**低风险信任模型，高风险看证据，不可逆交给人**。

## 7. 防"造假"的最小组合（不是无限核验）

| 风险 | 最小对策 | 是否递归 |
| :-- | :-- | :-- |
| 标绿没做 | done 必须带 E1/E2；无证据记 `done-unverified` | 否 |
| 改短清单 | 基线冻结 + 删改要 reason | 否 |
| 标准被放宽 | 标准冻结在批准时，改要新卡 | 否 |
| 证据伪造 | 证据来自进程/文件系统，不是模型自述 | 否（信任基到此为止） |
| 模型判偏 | 语义项一次单发 + 抽样人审 | 否 |
| 校验器自身有 bug | 单元测试 + 抽查；**不**在运行时校验校验器 | 否 |

最后一行的取舍要明说：**我们接受"校验器可能有 bug"这个残余风险**，用测试和抽查控制，而不是运行时递归验证。任何系统都有信任基，问题只是把它放在哪里、说清楚。

## 8. 验收标准（可测）

| # | 标准 | 怎么验 |
| :-- | :-- | :-- |
| V1 | 每张卡证据条数 ≤5、语义判定 ≤1 次、总时长 ≤30s | 埋点统计 |
| V2 | 任意 confirmed 卡，至少一条 E2 证据；纯 E0 不得 confirmed | 造一张只有自述的卡 |
| V3 | 证据可点开看原文，带哈希与时间 | 走查 5 张卡 |
| V4 | 不存在"验证器调用验证器"的代码路径 | 代码扫描 + 架构测试 |
| V5 | 语义项判定输入是冻结快照，判定后不再复议 | 检查调用参数 |
| V6 | 低风险卡允许仅 E0/E3，但必须进抽样审计池 | 造 read 卡 |
