## 2. 问题清单（含建议修法与可写测试）

> 按 Lead 要求：只报不改。每条给「现象 / 证据 / 根因 / 契约或接口层修法 / 可写成什么测试」。

### 2.1 P0（安全边界被绕过）：`/todo` 的 actor 可自报

- **现象**：执行者把 `actor` 写成 `user`/`decision` 即可标 done、冻结基线；`executor` 只是「诚实调用者」才被拦。
- **证据**：`routes/todo.ts:28`（`asString(body.actor) || 'executor'`）+ `:33`（只拦 executor）；探针 §1.3 全表；落盘验证 `frozen=true / 2/2 done`。
- **根因**：把「写入者身份」当请求参数，而不是可信会话的事实。
- **修法（契约/接口层）**：`POST /todo` 改收 `{caseId, planId, planNonce}`，服务端用**派发时下发给执行者的一次性凭据**判定身份（或由 scheduler 在 dispatch 事件里记 `executorToken`，executor 只能出示它）；`actor` 不再由客户端决定，服务端写死 `executor`；`freeze` 只允许 `authority=user/delegated` 的批准路径触发（或独立 `POST /todo/freeze` 只接受用户动作）。
- **测试**：① `actor:'executor'` done/freeze → 403（已有）；② `actor:'user'` done/freeze → **403**（当前 200，新增后应拦）；③ 缺 nonce / 错 nonce → 403；④ 正确 executorToken + done → 200；⑤ 用户批准路径 freeze → 200。

### 2.2 P1：`planNonce` 是死控制且暴露

- **现象**：nonce 生成了但从不校验；且 `GET /cards` 原样下发；注释「nonce 只留在卡上（执行者拿不到）」不成立。
- **证据**：`action.ts:37-45`（唯一赋值）、`routes/evidence.ts:24-26`、`routes/todo.ts:31`（都只比 planId）；探针 §1.6 的 `GET /cards` 4/6 带 nonce。
- **根因**：设计升级（nonce 绑一次性动作）只落了一半。
- **修法**：二选一——① 让 nonce 真正参与校验（`/evidence`、`/todo`、`gate.allowOnce` 都要求 `planNonce`，且**从 API 投影里剔除**：`GET /cards` / `/case` 序列化时 strip `planNonce`）；② 删掉 nonce，别做成安全剧场，并在 contracts.md 说明「绑定靠 planId + 服务端身份」。
- **测试**：错/缺 nonce → 403；`GET /cards` 与 `GET /case` 响应 JSON **不含** `planNonce`；正确 nonce 才 200。

### 2.3 P1（过收口）：`acceptance` 在生产没有写入点

- **现象**：生产卡批准后 `/evidence` 恒 `NO_ACCEPTANCE`；E2 证据链在生产不可达，任务卡永远无法 confirmed（决策卡靠回执仍可）。
- **证据**：全仓库 grep `acceptance` 只命中 contract schema、`Store.create` option（`store.ts:41,141`）、`routes/evidence.ts`、verification；**observer/decision/`POST /cards` 均不写**。仓库测试也是直接 `new Store().create({acceptance})` 造数据。
- **根因**：P0-4 关掉了外部证据入口，但「acceptance 由谁产出」这一环没接。
- **修法（契约层）**：`CardDraft` 增 `acceptance?: Acceptance[]`（observer 草稿可给、`POST /cards` 可带）；decision 票拟可建议 `acceptance`；**批准时 freezePlan 才把它落成不可改的 `card.acceptance`**（已有冻结语义）；同时 P1-5「Todo 注入」一起做，否则 B 类分流仍无输入。
- **测试**：① observer 草稿带 acceptance → 建卡后有 `acceptance`（未冻结标记）→ 批准后冻结；② `POST /cards {acceptance:[…]}` → 卡上可见；③ 无 acceptance 的卡 `/evidence` → `NO_ACCEPTANCE`（已有）；④ 有 acceptance 的卡 `/evidence` → E2 → verify confirmed。

### 2.4 P2：陈旧证据复用（reopen 后不清空）

- **现象**：reopen → 再批准 → 旧 E2 证据仍能 confirmed（证据数不变）。
- **证据**：探针 §1.6 最后一行；`freezePlan` 对已有 planId 早退（`action.ts:38`），reopen 不清证据。
- **修法**：`planId` 带 attempt（`cardId:seq:attempt`）或 reopen 时写 `evidence.supersededAt` 并把旧证据排除出验收；新 plan 生成时递增 attempt。
- **测试**：reopen → 再批准 → 无新证据时 verify 应为 `unknown/failed`，补新 E2 后才 confirmed。

### 2.5 P2：证据累计无上限 / `MAX_CHECKS` 语义

- **现象**：同一 acceptance 反复收集，8 次 → 8 条（设计 ≤5/卡）。
- **修法**：`EvidenceStore` 增「同 planId#acceptanceId 只保留最新一条」或累计上限；`MAX_CHECKS` 注释改为「acceptance 条数上限」。
- **测试**：同一 acceptance 收集 6 次 → 记录数 ≤5（或只保留最新）。

### 2.6 P2：测试缺口

现有 P0-4 用例（`kernel-routes.test.ts:247/256/265/296`）只覆盖 `actor:'executor'`、正确/错误 planId、PLAN_BOUND；**没有** actor 伪造、nonce 暴露/校验、陈旧证据、证据累计上限的用例。建议把 §2.1/§2.2/§2.4/§2.5 的测试补进 `kernel-routes.test.ts`（或新 `tests/host/plan-binding.test.ts`）。

## 3. 威胁模型说明（为什么这些绕过值得修）

`host/fence.ts` 的栅栏允许 loopback（`127.0.0.1`/`localhost`）直通；在本环境里，**被指挥的 agent 与插件同容器**，用 `curl 127.0.0.1:<port>/dsh-task-cards/api/*` 即可访问面板 API（不需要浏览器登录态）。因此：

- 「`actor` 是客户端字段」= 执行者可以自称 user → 清单自证绕过的现实路径成立；
- 「planId 可预测 + nonce 不校验」= 执行者能触发/重复触发证据收集（证据本身是真跑 checker，不算伪造，但能刷、能在自己方便时点）；
- `GET /cards` 暴露 nonce 在「loopback 可达」前提下是确定的泄露面。

若认为「同容器 agent 不可信」不成立（信任边界只到人），则 §2.1/§2.2 可降级为 P2，但需要在 `contracts.md` 里明确写出信任边界；当前文档写的是「执行者拿不到 nonce / 不能自证」，与实现不一致，属于文档-实现偏差。
