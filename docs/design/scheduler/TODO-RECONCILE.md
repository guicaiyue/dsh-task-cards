# Todo 作为执行清单：验收简化、未完成分流与会话对账

> 承接 [A-core 方案](A-CORE-PLAN.md) 与 [交互细化](UI-UX-SPEC.md)。本文回答两件事：
> ① 任务卡派发时给会话一份 **Todo 清单**，能否让验收变简单、并解释"为什么没完成"；
> ② 如何**拉取会话做对账**，把明确已处理的卡失效。
> 结论先行：**Todo 应做，但只能当"进度与结构"，不能当"事实"**；对账应做，但**判定必须有确定性证据，LLM 只提议**。
> 原型已同步：详情五段含「执行清单 3/5 · 1 blocked」，工作台带「对账」摘要（见 [prototype/](prototype/)）。
> 2026-11-09 拍板：**清单基线由执行者第一轮提议、秘书确认后冻结（方案 B）**；**对账默认直接失效但留痕、可重开**。证据取哪些、取到什么程度见 [EVIDENCE-MODEL.md](EVIDENCE-MODEL.md)。

---

## 0. 为什么这个想法是对的

现在的验收是"回读会话 + 人工/模型判断"，有三个天然缺陷：

1. **不可增量**：只看到"成/不成"，看不到做到哪一步；
2. **不可解释**：没完成时说不清是中断、忘了更新、还是代价变高；
3. **不可对齐**：卡片的 acceptance 是审批时写的，会话执行时可能早就跑偏。

Todo 清单同时解决这三件事：

| 缺陷 | Todo 带来的能力 |
| :-- | :-- |
| 不可增量 | 每个 item 的状态就是进度；`3/5` 比"执行中"信息量大得多 |
| 不可解释 | 未完成时能分流：中断 / 忘更新 / 代价变高 / blocked |
| 不可对齐 | 派发时冻结清单 = 执行契约；执行中可以加子项，但不能悄悄改目标 |

**但它不能替代机器验收**。Todo 是执行者的自述，不是事实；把它当唯一判据，等于让执行者自己判自己（A-core 里明确禁止的行为）。

## 1. Todo 契约

### 1.1 谁写、写在哪

- **谁写**：执行者（会话适配器里的 agent，或 system adapter 的步骤机）。
- **写在哪**：`plans/<planId>/todo.json`（append-only 事件 + 当前快照），并同步为 `CaseEvent(type=todo.updated)`。
- **怎么读**：调度者只读；验证器只读；面板展示；决策者读摘要。

```ts
interface TodoItem {
  id: string
  /** 派发时冻结的原始描述；执行中可以加子项，但改动原文要留 reason。 */
  text: string
  parentId?: string            // 支持一层子项，不做无限嵌套
  status: 'pending' | 'doing' | 'done' | 'blocked' | 'skipped'
  /** done 的证据：命令退出码 / 文件哈希 / URL / diff 片段。 */
  evidence?: { kind: 'exit' | 'file' | 'url' | 'diff' | 'text'; ref: string }
  /** 这条工作量的变化：正常 | 变大 | 变小；变大要给原因。 */
  cost?: { delta: 'same' | 'up' | 'down'; reason?: string }
  blocker?: string
  updatedAt: number
}

interface TodoList {
  planId: string
  items: TodoItem[]
  /** 派发时的基线，用于识别"目标漂移"。 */
  baselineIds: string[]
  revision: number
}
```

### 1.2 三条硬规则

1. **done 必须带证据**：没有 `evidence` 的 done 一律记 `done-unverified`，由机器项或决策者复核；纯 system adapter 可自动补证据。
2. **基线不可静默改**：**执行者第一轮提议 → 秘书确认后冻结**（方案 B）；冻结后允许新增子项（拆分工作），**删除或改写基线项必须给 reason 并触发一次复核**。冻结前的提议稿对用户可见但不计入完成率。
3. **清单不是验收标准**：acceptance（machine / evidence / manual）仍是硬门槛；Todo 只用来**推进度、分类未完成、给证据线索**。

## 2. 验收怎么被简化

原来的验收 = 逐条 acceptance 判。

新的验收 = **先看清单，再验硬门槛**：

```text
todo 全部 done 且证据齐  ──┬─ acceptance 全过 → confirmed
                            └─ acceptance 有不过 → failed（执行没做到 / 标准过严）
todo 未全部 done ───────────→ 进入第 3 节的三类分流
```

好处：

- 大部分成功场景不需要"回读会话猜"，看清单 + 机器项即可；
- 失败场景能立刻区分"没做完"和"做完了但不符合标准"，排障更快；
- `3/5 完成` 可以直接显示给用户，不用等结束。

**注意**：todo 全绿但机器项失败时，**不能**判通过——这正是"agent 自证"的典型失败模式，必须被硬门槛挡住。

---

## 3. 未完成时的三类分流（你提的核心）

会话结束时清单没做完，验证器按证据分三类，每条都有固定的下一步：

| 类型 | 判据 | 下一步 | 用户感知 |
| :-- | :-- | :-- | :-- |
| **A 异常中断** | 会话报错 / 超时 / 被抢占 / 无回执 | plan → `unknown` 或 `failed`；按 effect 决定重试或补偿 | 「执行中断（原因）」+ 重试/补偿 |
| **B 正常结束但忘更新** | 会话正常结束、有最终回复、清单项明显已完成但状态没改 | **继续这张卡**：给会话一次"对账并更新清单"的机会（受 1 次上限） | 「清单落后于实际，已让会话补更新」 |
| **C 代价变高 / 被阻塞** | 清单项 `blocked`，或 `cost.delta=up` 且超过阈值，或会话明说需要更大改动 | **交决策者评估**：继续 / 缩小范围 / 终止；判不了再升级用户 | 「代价变大：<原因>，等你定/等秘书定」 |

这份分流的价值在于：**同一种"没做完"，处理动作不同，且都能解释**。没有 todo 时，这三种在数据上长得一样（都是"没完成"）。

### 3.1 C 类的"代价"信号从哪来

不能靠验证器猜，要显式通道，三选一（推荐前两条）：

1. 清单项 `cost.delta=up` + `reason`（执行者主动标）；
2. 会话最后一条消息带结构化块 `{"cost":"up","reason":"..."}`（提示词约定）；
3. 机器指标（耗时/改动行数/失败重试次数）超阈值，作为辅助证据。

决策者的输入是：基线清单、当前清单、diff 摘要、cost 原因、历史判例；输出是 `continue / rescope / abort`。

## 4. 防止 Todo 变成"假账"

这是这个想法最大的风险：**agent 可以把清单改短、把项标绿**，让验收"看起来"通过。四条防线：

| 风险 | 防线 |
| :-- | :-- |
| 标绿但没做 | done 必须带证据；无证据记 `done-unverified`，不让进 confirmed |
| 删项/改目标 | 基线冻结 + 删除/改写要 reason + 触发复核 |
| 拆得太碎刷进度 | 顶层项数固定，子项不计入完成率分母；完成率只按基线项算 |
| 清单与结果不一致 | 交叉校验：机器项（exit/文件/API）优先于清单自述 |

另一个隐性风险是 **Goodhart**：一旦"全绿"变成 KPI，agent 会倾向于标绿。所以面板对用户展示的是「✓ 3/4 · 1 项 blocked」，而不是单一百分比；决策者看到的也是原始清单而不是打分。

## 5. 会话对账与失效（第 1 条需求）

### 5.1 要解决的问题

卡建了、没人处理，但事情**其实已经在会话里做完了**（用户自己做了、后来的轮次做了、或者另一张卡覆盖了）。这些卡留在工作台里是噪音，也会让"待我决定"虚高。

### 5.2 什么时候跑

| 触发 | 说明 |
| :-- | :-- |
| 启动时 | 扫一遍所有 open 卡，做一次对账 |
| 会话空闲后 | 某会话 `agent/status=idle` 且有待处理卡 → 对该会话的卡做一次 |
| 手动 | 工作台「对账」按钮 / 记录屏入口 |
| 定时 | 每天一次兜底（可关） |

### 5.3 判据（先确定性，后模型）

对每张 open 卡，按顺序检查：

1. **确定性证据（可直接失效）**
   - 后续轮次出现了同一指令的执行结果（commit、文件变更、命令输出）；
   - 卡片要求的产物已存在（文件/分支/API 状态）；
   - 同一会话已有内容等价、但更新的卡（`superseded`）。
2. **明确表态（可失效，需引用原话）**
   - 用户在会话里明确说"这个不用了 / 已经处理了 / 并入 X"。
3. **模型提议（不能直接失效）**
   - 观察者/决策者认为"看起来已处理"，只能产出 `propose-invalidate`，由决策者确认或用户一键确认。

### 5.4 判定结果与动作

**默认策略（2026-11-09 拍板）**：确定性证据成立时**直接失效**，但保留证据快照、可在面板一键重开；模型提议仍只作建议。

| 判定 | 卡状态 | 动作 |
| :-- | :-- | :-- |
| `handled` | `invalidated` | 写 `CaseEvent(reconcile, reason, evidence)`；从待处理移除；进历史 |
| `superseded` | `invalidated`（reason=superseded-by:c-xx） | 同上，并互链 |
| `stale` | 保持 open，标 `stale` 标记 | 提示"可能已过期"，让你决定 |
| `unclear` | 保持 open | 不动作，进"待确认"列表 |

### 5.5 安全护栏（必须有）

1. **永不静默删除**：失效 = 状态迁移 + 事件 + 证据，卡仍可搜到、可重开；
2. **失效不是万能的**：`destructive`/`spend` 类卡不自动失效，只能提议；
3. **可逆**：一键「重新打开」，恢复为 open 并写事件；
4. **有汇总**：每次对账后给一条摘要「本次对账：3 张已处理（可复核）、1 张疑似过期、其余不变」；
5. **可审计**：记录屏可按 `reconcile` 过滤，看到谁在什么时候因为什么失效了哪张卡。

### 5.6 新增状态

卡状态增加两个：`invalidated`（已失效）、`superseded`（被更新卡取代，可并入 invalidated 的 reason）。plan 增加 `cancelled`（已有）用于对账时撤掉未派发的计划。

## 6. 与 A-core 的映射

| 能力 | 依赖 | 阶段 |
| :-- | :-- | :-- |
| Todo 契约与事件 | `TodoList` + `todo.updated` 事件 + `plans/<id>/todo.json` | M1（随执行器一起） |
| 验收用清单 | `verification` 读 todo，先分类后验硬门槛 | M2 |
| C 类分流 | `cost.delta` / `blocker` + 决策者入口 | M2 |
| 对账与失效 | 会话读取 + 三类判据 + `invalidated` 状态 | M1（确定性部分）→ M2（模型提议） |
| 面板 | 详情「执行清单」段 + 工作台失效态 + 对账汇总 | M3 |

**建议顺序**：M1 先把 Todo 与事件打通（只展示与记录，不参与判定）；M2 再让验收读它；对账的确定性部分（产物已存在/superseded）跟着 M1 做，模型提议放 M2。

## 7. 验收标准（可测）

| # | 标准 | 怎么验 |
| :-- | :-- | :-- |
| T1 | 派发后会话能拿到清单，每完成一项写 `todo.updated` + 证据 | 造 3 项任务，看事件流 |
| T2 | 全绿 + 机器项全过 → confirmed；全绿但机器项失败 → failed | 两个用例 |
| T3 | 未完成时能分出 A/B/C 三类，动作不同 | 造中断 / 忘更新 / cost up 三个用例 |
| T4 | B 类只给一次补偿机会，第二次不再自动继续 | 连续两轮不更新清单 |
| T5 | 删基线项/写短清单会被识别并触发复核 | 手动改清单 |
| T6 | 对账能失效"产物已存在"的卡，且可一键重开 | 造一张已完成但未关的卡 |
| T7 | 失效不静默：记录屏可按 reconcile 过滤，含证据与原话 | 走查 3 条 |

---

## 8. 不做什么

- 不做无限嵌套的 todo 树（一层子项够用）；
- 不做"全绿即通过"的自动关单（机器项必须过）；
- 不让模型单独决定失效（只能提议）；
- 不把 todo 当对外承诺（它是内部执行清单）；
- 不为 todo 单独做一套 UI 体系（复用时间线段的样式）。
