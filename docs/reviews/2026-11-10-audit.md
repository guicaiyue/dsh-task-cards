### 事故 1：回合内不可逆动作没被拦（准备对生产库 ALTER TABLE，人工叫停）

- **现象**：开发 agent 在回合中途准备直接对生产库 `ALTER TABLE`，插件全程无感知；人肉叫停。

### 事故 2：同一句答复被派发两次（重复派发）

- **现象**：pREST 卡被批准两次，会话收到两条相同的「任务卡答复 c-mw958ol4」。
- **证据**：journal `cards.json.journal/c-mw958ol4-3gtes.jsonl` 完整记录两轮：
  `10:57:01 idle→waiting`（用户批红）→ `leased → dispatched → executed → verifying → unknown`；
  `10:57:35 unknown→waiting`（用户**再次**批红）→ 同样的 5 步再跑一遍。
  `04-dev-log.md:27,64`、`05-task-card-review.md:13,27-32`。
- **代码定位**：`src/host/routes/action.ts:178-191` 的 `assertApprovable` 只拦 `waiting/leased/dispatched/executed/verifying/confirmed`，**漏了 `unknown`、`failed`、`invalidated`，也没看 `status`**；而 `unknown` 恰恰是当时每张卡的终止态（`verifier` 判 unknown 后 `status` 仍 open），于是第二次 approve 一路通过 → `transition unknown→waiting` 合法（`src/shared/case.ts:105-110`）→ 再派一次。现有回归用例只覆盖 `waiting` 状态（`tests/host/kernel-routes.test.ts:174-181`）。
- **附加重复路径**（代码级，未在真实数据中触发）：(a) `#dispatch` 在 adapter 成功但后续 `#move('dispatched')` 抛错时会退回 `leased`→TTL 到期重排，已投递的消息不会再被撤销（`scheduler.ts:89-104`）；(b) 没有 `idempotencyKey` 落盘，scheduler 崩溃恢复后无法识别「这张已投过」。
- **根因**：幂等闸门按「在飞状态枚举」写死，而不是按「已产生投递事实」判定；投递账里没有幂等键。
- **现状**：部分修复（面板不再显示批准 + in-flight 枚举），**unknown/failed 通道仍开着**。
- **修法（契约层）**：`ApprovedPlan` 引入 `idempotencyKey = cardId + decisionSeq`（或 `traceId + attempt`），scheduler 在 dispatch 前写 `dispatched` 事件并校验 key 未出现过；`approve` 前判定改为「`status` 已结束或 `deliveryState` ∈ 非 idle ⇒ 一律 `ALREADY_APPROVED`，重批必须显式 `reopen`（`invalidated/unknown/failed → idle` 迁移）再批」。
- **测试**：`approve → 强置 unknown → approve` 断言 400；同一 `idempotencyKey` 连续两次 tick 只派一次（统计 adapter 调用次数 = 1）；journal 里 `dispatched` 事件按 key 唯一。

### 3.4 对 P0-3（生命周期单一真源）落地的两个校验点（Lead 点名，优化员正在改）

**(1) `src/host/scheduler/queue.ts::isCandidate` 的语义**

现状：`isCandidate(card) = deliveryState === 'waiting' && !isClosed(status)`（`queue.ts:11-13`），`isClosed` 含 `acknowledged`（`shared/state.ts:6`）。

- **「acked 会被当可派发」：不会。** 任何 `status ∈ {acknowledged, done, dismissed}` 的卡都被 `!isClosed` 挡在派发之外。
- **真正的风险是反向的：`acknowledged` 的 waiting 卡会静默卡死。** `ds=waiting + status=acknowledged` 既不会被派发，也不会产生 `waitReason`/事件/告警，`/case`、`/progress`、`/records` 上都查不到原因——这是又一条「两套状态打架」的隐形路径（§3.2 W4 的近亲）。能产生该组合的路径：`/action acknowledge` 对所有卡开放（`ACTION_RESULT`，`shared/state.ts:13-23`）+ 批红入队只改 `answer` 不改 `status`（`routes/action.ts:211-224`）；`Store.markSeen` 本身不校验 kind（`store.ts:154-161`），只有调用方 `markRecentInfoCardsSeen` 过滤了 `kind==='info'`（`observer/seen.ts:41-57`）。
- P0-3 落地时**必须同时满足三条**，否则只是把矛盾从「两套状态」换成「一套状态 + 隐形死卡」：
  a) `statusForDelivery` 只对 `deliveryState !== 'idle'` 生效（optimization-plan 里已有此约束，别在实现时漏掉）；
  b) 在 `transition()` 里加反向约束：`to==='waiting'` 时若 `status` 已关闭 → 要么拒绝（400 `BAD_STATE`），要么同一次 patch 内打开 status 并写事件，不能静默共存；
  c) `isCandidate` 改为只看 `deliveryState`（人关掉的卡应由 `done/dismissed → cancelled/invalidated` 的显式事件取消计划），否则 `acknowledged` 永远是一堵看不见的墙。
- 可写成测试：`acknowledged + waiting` 的卡 tick 后必须二选一（被派发 / 被显式取消并写事件），不允许「既不派发也无原因」；`done + waiting` 同理；`acknowledged 后重新 approve` 的幂等断言。

**(2) `unknown` / `failed` 卡在面板上的可发现性**

现状：阶段徽标对（`client/stage.ts:31-32` → 未知/失败），`需关注` 过滤按 `deliveryState` 命中（`stage.ts:124`），`FailureTab.tsx` 专门列这两类 → **能找到，但会被忽略**，有三处具体原因：

- a) 行内主操作被替换成「已批准，执行中」chip（`client/components/CardActions.tsx:27-29` 只排除 `idle/invalidated`）——unknown/failed 明明不在飞却显示在执行中，而且**行内没有任何重试/重开/补偿入口**，用户点不进去只能开详情。
- b) `attention` 的 KPI 与过滤都不看 `status`（`stage.ts:87-99,124`）：`attention += 1` 在 `if (!open) continue` **之前**，所以已关闭的 unknown 卡同时进「需关注」和「已关闭」——真实数据就 3 张（§3.3），数字虚高、同一张卡数两次。
- c) 若 P0-3 把 `failed`/`unknown` 映射成关闭态，`CardRow` 的 `closed=true` 会让 `PrimaryAction` 整块不渲染（`CardActions.tsx:174`），行内**一个动作都不剩**，只剩「详情」——从「看不见问题」变成「看见了也动不了」。
- 建议：把 `attention` 定义收成一条表达式「`deliveryState ∈ {failed, unknown}` 且 `waitReason !== null`（还欠一个处置）」，`kpiOf` 与 `filterCards` 共用它；行内对 `failed` 给「重试」，对 `unknown` 给「重开 / 授权补偿 / 作废」，并把「谁欠处置」显示出来（`awaiting-user-escalation` = 等你定，`awaiting-decision` = 等秘书）；`invalidated` 单独计数，别混进 attention。
- 可写成测试：`failed`/`unknown` 卡渲染出对应动作（不是 chip）；`done + unknown` 只出现在一个过滤里；`unknown + awaiting-user-escalation` 行内出现「等你定」；KPI 与过滤对同一批卡给出相同数量。

## 4. 关键判断：闭环断在哪

```text
观察者 ──建卡──> 决策/批准 ──入队──> 调度 ──dispatch──> 会话
                                             │
                                    ✗ 这里把「已投递」当「已执行」
                                             ▼
                         验收 ──读 todo/evidence──> 生产数据里两者都没有
                                             │
                      决策卡：无条件 confirmed（假通过）
                      其它卡：unknown（永久，无人消费）
                                             ▼
                          status 不跟随 → 面板继续显示「待我决策」
```

**闭环的两个断点**：
1. **执行回执断点**（`execution/session.ts:31-41` + `scheduler.ts:107-117`）：没有「回合结束/ExecutionResult」这一环，验收必然空转。
2. **状态回写断点**（`verifier.ts:73-122` + 所有 status 直写点）：验收结论不回写 `status`，卡片生命周期在面板上不收敛。

其余问题（闸门缺失、观察者漏看、数据覆盖丢失）都是围绕这两个断点的放大器。

**P0-2 批准幂等仍有 unknown/failed 通道 + 投递缺幂等键**（事故 2）

**P0-3 执行完成判定错：投递即执行 → 验收在做事之前跑**（☆ 计划未覆盖）

- 修法：`adapter.execute` 返回值改 `{accepted, via, turn?}`；新增 `deliveryState: 'dispatched'` 的**回执等待**：监听 origin 会话 `agent/status=idle` 且 turn 号 > 派发时 turn → 落 `executed`（写 ExecutionResult：`{planId, executor, evidence[], durationMs, turn}`）；`DTC_VERIFY` 的自动验收移到 `executed` 之后触发，而不是同一个 tick。

**P0-4 台账可自证：/evidence 可执行任意命令 + 清单/证据无写者校验**（☆ 计划未覆盖）

### P1（让人多干活 / 结论不可信，但不直接造成损失）

**P1-1 决策卡无条件 confirmed（假通过）**（☆ 语义需改）
- 现象：任何 `kind==='decision'` 的卡无清单无证据也 confirmed（`verify.ts:54-63`），EVIDENCE-MODEL V2 被违反，事故 A 的「unknown 停卡」被临时补丁掩盖而不是修好。
- 修法：决策卡的验收标准应是「答复已投递到 origin 会话且该会话确实继续了一轮（回执）」= E2/E3 证据，而不是 `kind` 白名单；把特判改成 `acceptance: [{kind:'evidence', check:'session.turn > dispatchedTurn'}]`。
- 测试：决策卡未产生回执 → 不得 confirmed；回执到 → confirmed 且有 E2 证据；E0-only 卡不得 confirmed（V2 用例）。

**P1-2 清单全绿但零证据也 confirmed（Goodhart 漏洞）**
- 现象：`verify.ts:126-139` 只要 `todo.frozen` 且全 done 就 confirmed，即使 `evidence=[]`；`todo/store.ts:133-134` 的 done-unverified 标记是空操作；`completionOf` 把 `skipped` 算完成。
- 修法：`done` 无 evidence → `done-unverified`（新状态或在 item 上加 `verified:boolean`），`confirmedOutcome` 要求「至少一条 E2 或决策者语义确认」；完成率分母排除 skipped 但分子不计 skipped。
- 测试：全绿无证据 → failed/unknown；全绿有 skipped → 不计完成；带证据 → confirmed；`done-unverified` 不得进入 confirmed。

**P1-3 dispatched 无超时回收 → WIP=1 变死锁**

**P1-4 票拟自动执行绕过内核（无事件/无验收/无 CAS）**
